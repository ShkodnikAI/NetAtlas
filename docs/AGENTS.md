# Агенты: подключение, регистрация, отзыв (NR-024)

Серверная сторона связи с агентами. **Выключено по умолчанию**: сервер
без явных флагов агентов не принимает — включать решает владелец.

## Что открывается

| Флаг | Назначение | TLS |
|------|------------|-----|
| `--agent-listen ADDR` | mTLS-слушатель агентов: `checkin`, `inventory` | TLS 1.3, `RequireAndVerifyClientCert`, корень — только наш CA (NETATLAS_KEYDIR) |
| `--agent-enroll-listen ADDR` | слушатель регистрации: `enroll` | TLS 1.3, клиентский сертификат не требуется (личности ещё нет), одноразовый токен |

Ограничения слушателя регистрации: не больше 10 запросов в минуту с
адреса, тело не больше 64 КБ. Тело инвентаря — не больше 2 МБ.
Агентские порты не могут совпадать с портом владельца и между собой;
нелокальные адреса (как и для `--listen`) требуют `--allow-remote`.

Агент всегда приходит сам (pull): сервер не инициирует соединений к
агентам. Личность агента — CN клиентского сертификата (`agent:<uuid>`);
тело запроса личность не задаёт (лишние и подменённые поля отклоняются
строгим разбором JSON).

## Маршруты

| Маршрут | Порт | Доступ |
|---------|------|--------|
| `POST /agent/v1/enroll` | enrollment | токен регистрации + CSR |
| `POST /agent/v1/checkin` | mTLS | сертификат агента |
| `POST /agent/v1/inventory` | mTLS | сертификат агента |
| `POST /api/agents/enrollment` | владельца | Bearer-токен |
| `GET /api/agents` | владельца | Bearer-токен |
| `POST /api/agents/{id}/revoke` | владельца | Bearer-токен |

## Порядок подключения агента

1. Запустить сервер с ключами PKI (NETATLAS_KEYDIR, см. docs/PKI.md)
   и агентскими слушателями:

   ```
   NETATLAS_TOKEN=... NETATLAS_KEYDIR=/var/lib/netatlas/keys \
     netatlas-server --db /var/lib/netatlas/netatlas.db \
       --subnets 192.168.1.0/24 \
       --agent-listen 0.0.0.0:8443 \
       --agent-enroll-listen 0.0.0.0:8444 \
       --allow-remote
   ```

   Сертификат сервера выпускается автоматически один раз и хранится в
   каталоге ключей (`server.pem`, `server.key`).

2. Получить одноразовый токен регистрации (живёт 1 час, в базе и
   аудите только хэш):

   ```
   curl -X POST -H "Authorization: Bearer $NETATLAS_TOKEN" \
     http://127.0.0.1:8484/api/agents/enrollment
   ```

3. Агент генерирует свою пару ключей и шлёт CSR (CN `agent:<uuid>`)
   с токеном на `POST /agent/v1/enroll`. В ответе — сертификат
   (90 дней, только ClientAuth) и интервал опроса. Закрытый ключ
   агента не покидает агента.

4. Дальше агент общается только по mTLS: `checkin` (heartbeat, список
   заданий — с NR-011) и `inventory` (порции данных: `kind`,
   `schema_ver`, `collected_at`, `payload`).

## Отзыв

- Агент: `POST /api/agents/{id}/revoke` на порту владельца.
- Сертификат (компромисс машины): `netatlas-pki revoke <serial>`.

Следующий handshake отозванного отвергается; список отзыва на
handshake кэшируется не дольше 10 секунд, поэтому после отзыва
действующее соединение закрывается следующей попыткой агента, а
отказы пишутся в журнал аудита (`agent_checkin/deny`,
`agent_inventory/deny`). Повторная регистрация того же CN (после
перевыпуска сертификата) возвращает агента в `active` — это осознанное
исключение для восстановления агента владельцем.

## Что пишется в аудит

`agent_enroll`, `agent_inventory`, `agent_link_macs`, `agent_revoke`,
`issue_enroll_token`, `consume_enroll_token`, отказы маршрутов
(`*/deny`). Успешные heartbeats (`checkin`) в журнал не пишутся:
при частоте опроса они раздули бы цепочку и замедлили её проверку
(`/api/audit/verify` идёт по всей цепочке).

## Сценарий для владельца (живой прогон)

Тесты покрывают серверную сторону в процессе (настоящий TLS на
127.0.0.1). Живой прогон с внешней машиной — вручную:

1. Поднять сервер по шагам 1–2 на машине с сетевым доступом.
2. Со второй машины выполнить enroll тестовым клиентом и убедиться,
   что `GET /api/agents` показывает агента, а устройства из
   mac_list получили класс `managed` на карте.
3. Отозвать агента и убедиться, что следующий checkin отвергается,
   а в `GET /api/audit` появились записи `agent_checkin/deny`.
