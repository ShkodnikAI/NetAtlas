# PKI NetAtlas: ключи, сертификаты, подпись заданий

Собственный центр сертификации (CA) NetAtlas выпускает сертификаты
сервера и агентов, ключ подписи заданий (ed25519) подписывает задания,
агент проверяет подпись перед исполнением (`agent/verify`). Только
стандартная библиотека Go: сертификаты — ECDSA P-256, подпись —
ed25519. Новых зависимостей нет.

## Где лежат ключи

Каталог ключей задаётся переменной окружения `NETATLAS_KEYDIR`
(обязательна). Утилита `netatlas-pki` без неё не работает.

| Файл | Что это | Права |
|------|---------|-------|
| `ca.key` | закрытый ключ CA (ECDSA P-256) | 0600 |
| `ca.pem` | сертификат CA (открытый, для агентов) | 0644 |
| `sign.key` | ключ подписи заданий (ed25519) | 0600 |
| `sign.pub` | открытый ключ подписи (для агентов) | 0644 |

Создание: `NETATLAS_KEYDIR=/путь netatlas-pki init`. Повторный запуск
на непустом каталоге отказывается перезаписывать ключи. Ключ CA хранится
отдельно от ключа подписи: компрометация одного не делает легальным
подписанный другим материал.

На Linux лишние права файла закрытого ключа (не 0600) — отказ загрузки.

## Ограничение Windows (права каталога)

Средства Go на Windows не выставляют POSIX-права. Владелец закрывает
каталог от других пользователей вручную:

```bat
icacls "%NETATLAS_KEYDIR%" /inheritance:r /grant:r "%USERNAME%:(OI)(CI)F" /remove *S-1-1-0 *S-1-5-32-545
```

Учётки — по SID, не по именам: well-known имена групп локализованы
(на русской Windows это «Пользователи» и «Все»), `/remove` с именами
падает с ошибкой 1332 — как в PR #86 с агентом. SID локали не зависят:
`*S-1-1-0` — Все (Everyone), `*S-1-5-32-545` — Пользователи
(BUILTIN\Users). После этого доступ к каталогу имеет только текущий
пользователь.
Проверка: `icacls "%NETATLAS_KEYDIR%"`.

## Резервная копия ключей

1. Скопируйте `NETATLAS_KEYDIR` целиком на носитель, хранимый отдельно
   от базы данных и от самой машины (ключи восстанавливают доверие,
   база без ключей бесполезна при переустановке).
2. Права копии проверьте тем же способом (0600 на `*.key`).
3. Копия делается после `init` и после каждой ротации.

## Ротация ключа подписи заданий

1. Выпустите новый ключ: временный каталог, `netatlas-pki init`,
   скопируйте только `sign.key` и `sign.pub` из нового каталога.
2. Замените `sign.pub` в каталоге ключей сервера; старый `sign.key`
   переименуйте (например, `sign.key.old`) — он нужен для проверки
   заданий, выпущенных до ротации, если такие ещё в очереди.
3. Раздайте агентам новый `sign.pub` (следующий выпуск агентов
   подхватит ключ при обновлении; до обновления агент продолжает
   проверять старым ключом).
4. После того как все агенты обновились, удалите `sign.key.old`.

## Ротация CA (полная, редко)

1. `netatlas-pki init` в новом каталоге — новый CA и новый ключ
   подписи.
2. Перевыпустите сертификат сервера и перевыпустите сертификаты всех
   агентов (новые CSR с одноразовыми токенами регистрации).
3. Раздайте агентам новый `ca.pem`; старый корень держите до конца
   перевыпуска (оба корня в доверии одновременно).
4. Переключите сервер на новый каталог; старый `ca.key` уничтожьте
   после завершения перевыпуска.

## Подозрение на компрометацию

- **Утек ключ подписи (`sign.key`)**: сгенерируйте новый (ротация
  выше), задания, подписанные утекшим ключом, агент отвергнет после
  обновления `sign.pub`; немедленно обновите ключ на всех агентах.
- **Утек ключ CA (`ca.key`)**: компрометированы все выданные
  сертификаты. Полная ротация CA (выше); до её завершения отзовите
  подозрительные сертификаты (`netatlas-pki revoke <serial> --db …`)
  — отзыва сервер и агент придерживаются при каждом handshake.
- **Утек закрытый ключ агента**: отзовите его сертификат по серийному
  номеру, выдайте агенту новый ключ и сертификат (новый CSR, новый
  токен регистрации). Закрытый ключ агента никогда не покидает агент:
  утечка возможна только с самого компьютера.

## Токены регистрации

`netatlas-pki enroll-token --db <путь>` печатает токен один раз (32
байта, hex, срок 1 час); в базе и аудите остаётся только SHA-256.
Токен одноразовый: повторное использование отвергается. Агент
отправляет токен вместе с CSR; сервер расходует токен атомарно и
подписывает CSR (`pki.SignAgentCSR`, сертификат агента — 90 дней,
ExtKeyUsage только ClientAuth).

## Что где проверяется

| Проверка | Где |
|----------|-----|
| Цепочка до CA, срок, отзыв | `pki.Verifier.VerifyPeer` (handshake) |
| Роль сертификата (client/server) | TLS-конфиг по ExtKeyUsage |
| Подпись задания, цель, сроки, повтор | `agent/verify.Verify` |
| Одноразовость и срок токена | `store.ConsumeEnrollToken` |
| Права файлов ключей | `pki.LoadCA`, `pki.LoadSigningKey` (Linux) |
